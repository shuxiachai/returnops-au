**This is a static mapping, not an acceptance.** It was prepared by reading test code; no test was run for it and no CI result is relabelled by it. "Asserts effects" means the test asserts rows of history, audit, effect, ledger or work tables, or the call count of a mock provider, not only response fields.

## R.02 end-to-end chain

The earlier draft of this map listed as a gap that no HTTP-level test runs from approval through return, label and notification. The R.02 driver now provides that chain for one synthetic case ([docs/41](41-r02-end-to-end-evidence.md)): Founder approval over HTTP, the private execution chain (admission, preparation, CREATE_RETURN, bridge, GENERATE_LABEL, label PDF, notification produce and send), then Founder read-back over HTTP. Its first CI receipt (run 39634415393, job `end-to-end-no-llm`) records these checks as true: `negative_customer_token_no_write`, `negative_wrong_fingerprint_no_business_change`, `negative_wrong_fingerprint_one_denial_audit`, `approve_replay_identical_receipt`, `approved_once`, `execution_work_pending_after_approval`, `zero_effects_after_approval`, `no_execution_grant_after_approval`, `prepare_keeps_case_version`, `return_ledger_mock_provider`, `label_ledger_mock_provider`, `operations_mock_providers`, `notification_sent_return_created`, `notification_channel_core_mock`, `history_order_decision_approval_operation_notification`, `audit_chain_linked`, `audit_chain_hashes_recomputed`, `audit_one_approve_denial` and `final_status_completed`.

This is one run of one case on primary paths only. The steps after approval are private service calls, because no public execution route exists by design. It is run evidence for R.02, not a parameterized E.10 test, and it does not replace the fault, concurrency or retention rows above.

## Gaps

1. Only DH01-DH07 drive PostgreSQL through HTTP, and they assert Domain table rows (history, audit, lifecycle), not provider ledgers. Provider-effect assertions are at the lifecycle layer (RE_G*, LE_G*, notification_*). DH04 allows a 503 on lock timeout; this is the contract written in the test and must not be described as "always 202".
2. DH01's kinds are only approve, reject, revision, manual_failure and manual_block. No HTTP-level parameterized test continues from approval to return, label and notification. The R.02 driver now covers that chain once, as described above; fault paths along it remain covered only at the lifecycle layer.
3. "No provider permission" was confirmed by reading for return creation (RE_G3) and order lookup only; the label and notification missing-permission cases are confirmed by name only.
4. The `tests/security` matrix tests mainly assert authorization decisions and error codes; whether they assert zero business writes is not confirmed. Zero-write assertions are confirmed in DH03, AP07 and RE_G3.
5. Timeouts: database lock timeouts (RE_G7, DH04's 503 path) and commit/close ambiguity (RE_G4_G8, notification T1/T2/T3) are covered; no test for an HTTP client read timeout was found (grep, not exhaustive).
6. `tests/founder/test_decision_http_boundary.py` is offline and is not evidence of concurrency, persistence or provider effects.
7. Item 6, "notification isolation", is not defined in the documents. This map reads it as "the notification is an independent fact, does not change the business result and causes no return or label effect". If E.10 means isolation across stores or cases, `tests/security/test_authorization.py::test_absent_and_cross_store_cases_have_the_same_safe_error` and the notification_fact_alias tests need to be checked as well.
