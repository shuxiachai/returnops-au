## 1. Executive Summary

This document specifies the deterministic demonstration fixtures, automated UI regression suite, and a choreographed 3-minute in-class demonstration script for Member B's web frontend (`returnops-au/apps/web`).

The frontend operates strictly as an untrusted client in Kruchten's 4+1 package decomposition (P01), delegating domain state transitions, statutory policy evaluations, and cryptographic audit recording to the backend gateway (P02) and core domain (P04). It supports transparent dual-mode execution:
1. **Offline Mock Mode (Default)**: Zero-setup deterministic demo fixtures for resilient live presentation without external network dependency.
2. **Live API Mode**: Requests are issued against the configured API base URL (`VITE_API_BASE_URL`; empty prefix by default, so requests go through the Vite dev-server proxy to the FastAPI gateway). Only operations that actually exist on current backend `main` are served. Founder analytics (`GET /v1/founder/analytics`) is registered by default and is read live. Founder decision recording (`POST /v1/founder/cases/{id}/decisions`) is registered only when the API is started with `--founder-decisions` (`RETURNOPS_FOUNDER_DECISIONS=1`). The live client then sends contract-exact requests. Without the flag, it reports the server's envelope-less `404` as `DECISION_ROUTE_NOT_SERVED` (nothing recorded).

> **Current implementation status (must stay accurate).** The frontend is a mock-first prototype: the deterministic fixture store backs every screen. Live reads are implemented for the operations listed in `apps/web/README.md` (section 1.3), including Founder analytics. Live writes are case creation, staged uploads and clarifications, plus Founder decisions, but only on a server started with the decision flag. One Founder decision has been sent from this UI to a real server: the 24 October 2026 pass 0 rehearsal sent `MANUAL_HANDLING` on an escalated case and the server refused it with `403 FORBIDDEN`, because `demo.py provision` then granted no manual-outcome capability (docs/47 section 5, step 14 and note 4). Since `demo.py provision --founder-manual` (#132), that decision is accepted: on 26 October 2026 `MANUAL_HANDLING` sent from this UI on an escalated case moved it to `NOTIFICATION_PENDING` (docs/47 section 5, "Local check of the S3 manual decision"), and the 27 October local run from a zip of `main` repeated it (docs/47 section 7, item 15). It is the only decision a real server has accepted from this UI; `APPROVE`, `REJECT` and `REQUEST_REVISION` are evidenced by stubbed tests. This document does not claim a complete live backend integration.

## 3. Choreographed 3-Minute Live Demonstration Script

### Scene 1: Customer Natural Language Lodgement (`UC-01`, 45 Seconds)
- **Actor Role:** Customer (`customer_demo_one`) on `http://localhost:5173`.
- **Action:**
  1. Open the Customer Service Portal (Lodge Return tab).
  2. Input natural language statement: *"I received the espresso machine yesterday but the heating element trips the safety circuit immediately upon turning it on."*
  3. Select Requested Outcome: `REFUND` (the form starts on "Not sure - let the shop advise", `UNSPECIFIED`).
  4. Attach staged proof: Upload receipt image `synthbrew_invoice.png`.
  5. Click **Submit Return Request**.
- **Talking Point:**
  > *"Notice how the customer describes their issue in natural everyday language. The frontend enforces RFC-compliant idempotency keys and packages staged multipart evidence attachments without evaluating business rules locally."*

### Scene 2: Targeted Supplementary Clarification (`UC-01E`, 45 Seconds)
- **Actor Role:** Customer switching to **Track & Clarify** tab.
- **Action:**
  1. Select quick demo case `case_demo_001` (Awaiting Information).
  2. Highlight the amber **A few questions for you** card (the customer no longer sees question-set or question IDs).
  3. Fill in answers:
     - Barcode question: *"Barcode is 9312345678901, tag attached."*
     - Parcel integrity question: *"Outer StarTrack parcel was intact."*
  4. Click **Submit Answers**.
- **Talking Point:**
  > *"Rather than forcing customers to re-fill generic forms, the intake stage asks only for what the case is missing. The questions are not written by an agent here: a deterministic rule in the domain service decides that purchase context is missing, stores the question set on the case, and the case view carries it to the page. The frontend submits the answers bound to the expected case version (v2), so a concurrent update cannot be lost."*

### Scene 3: Founder Governed Review & Double Approval Guard (`UC-04`, 60 Seconds)
- **Actor Role:** Store Founder navigating to **Founder Console & Governance**.
- **Action:**
  1. Review queue table; filter by status `AWAITING_APPROVAL`.
  2. Click **Inspect** on `case_demo_003`.
  3. Cycle through modal tabs:
     - **Proposal & Risk Review**: Show the Assessment Proposal (`recommended_action: PROPOSE_REFUND`, refund amount `$220.00` — a demo-only display field, since the v1 `DecisionPacket` carries no refund amount — and rationale) and the Risk Review (`outcome: PASS`, findings, `reviewed_at`). The **Source** tile says who produced the proposal: "Not recorded" for the mock data, "Fixed rule-based proposal (no model)" for the live Gate 1 proposal, and a confidence appears only next to a real model ID.
     - **Order & Facts Projection**: Inspect the contract-shaped `OrderSnapshot` — `order_id ord_7731`, `purchased_at`, `snapshot_version: 1`, and its single `line_item` (`French Linen Sheet Set (Queen, Oatmeal)`, SKU `LN-SHT-QN-OAT`, `unit_price_minor: 22000`). This tab renders **only** fields the contract actually carries; it does not display carrier or order-total fields that the snapshot does not contain.
     - **Tamper-Evident Audit Chain**: Display the recorded event history and its hash and previous-hash fields (fixture values in Mock Mode; not a SHA-256 digest), which the demo presents as an immutable-event indicator. The banner reflects recorded events; the demo does not recompute the chain (see the limits in Section 4).
  4. Click **Approve Return** in the footer.
  5. In the confirmation, point out the approval scope: preview ID `prev_demo_003`, the scope fingerprint, the `CREATE_RETURN` and `GENERATE_LABEL` commands, the `$0.00 AUD` amount ceiling and the expiry.
  6. Enter mandatory governance rationale: *"Verified unopened goods within 30-day change of mind window."*
  7. Click **Record decision**. The case reopens on the **Decision & Outcome** tab: the decision with its rationale and the approval of the exact scope; in Mock Mode no operation follows. For a finished case, open `case_demo_005` and its **Decision & Outcome** tab: both simulated operations, **Download label (PDF)** and the sent notice to the customer (#122 item 4).
- **Talking Point:**
  > *"Crucially, the UI does not allow arbitrary approval. The confirmation shows the exact scope the Operations Service previewed, and the approval request binds that preview_id and scope_fingerprint. Both are copied from the server's case view; the browser never invents them. If the proposal or preview changes during review, the server rejects the approval. Approval alone runs nothing: the button records a decision. Be precise about this scene, though: it runs in Mock Mode, so the approval is recorded against the mock store. In live mode the same request goes to `POST /v1/founder/cases/{id}/decisions` when the API runs with `--founder-decisions`. The automated tests pin that request body, but it has not yet been sent to a real server from this UI. Section 4 lists exactly what this suite does and does not evidence."*

### Scene 4: Operations Analytics & Latency Monitoring (`OF-006`, 30 Seconds)
- **Actor Role:** Founder switching to **Analytics Dashboard**.
- **Action:**
  1. Showcase total volume throughput (128 cases), unreviewed backlog (58 cases).
  2. Point out latency percentiles ($p50$ at 11.20s, $p95$ at 46.50s; the tile no longer says "SLA", because no service level is promised) and the counts beside them (measured 70, failed 2, unmeasured 56: together the 128 cases). Live, latency is at tier 0: the tiles read "Not measured" and only the counts are filled.
  3. Review status distribution progress bars and risk review outcome breakdown.
- **Talking Point:**
  > *"The analytics dashboard aggregates operational facts across the lifecycle in one server query, so the store owner sees case volume, status distribution and risk outcomes without the browser counting anything. Latency is at tier 0 today: the tiles read 'Not measured' until the backend has trusted start and end events, and we would rather show nothing than a number we cannot defend."*

Three further limits are worth stating plainly. First, the Founder detail cards render a small set of **frontend-only demo extensions** that the v1 contract does not carry as fields (`refund_amount_cents`, `return_label_required`, `risk_score`, `summary`, `policy_citations`, `action_preview.operation_type`, `action_preview.details`); `apps/web/src/types/domain.ts` labels them as such, and the contract's citation data lives elsewhere (`DecisionPacket.citations`, `RiskFinding.citation_ids`, the latter already present in the mock findings). Second, the **Tamper-Evident Audit Chain** panel reflects the presence of recorded audit events and their fixture `event_hash`/`previous_event_hash` values; no test recomputes the hash chain. The banner therefore reads "Recorded Audit Events", uses neutral rather than success styling, and states that the view does not recompute or verify the chain: it shows each recorded hash and, where present, the previous-hash link, not a verified cryptographic linkage. `FounderConsole.test.tsx` asserts that sentence. Third, the confirmation-modal **stacking** fix (Finding 3) is evidenced by the emitted stylesheet (`z-[60]` present in the built CSS), not by the jsdom tests — jsdom does not compute paint order, so the reachability assertions and the CSS check are two separate pieces of evidence. The evidence gate is exercised for an *unstaged* file on both forms. For a file that is still *uploading*, both forms assert the submit button disabled (`CustomerPortal.state-races.test.tsx`), but only the clarification form also forces a submit and asserts the handler's wait message; the lodgement wait message is not asserted.

Every one of these suites runs in the CI `web-frontend` job (`.github/workflows/ci.yml`), whose steps run in this order: `npm ci`, `npm run type-check` (`tsc --noEmit`), `npm test` (`vitest run`), then `npm run build` (`tsc && vite build`). The job runs beside the final `api-environment` gate rather than inside it: it is not in that job's `needs`, which `tools/checks/run.py ci-gate` requires to be exactly `offline-contract-models`, `environment-plan` and `environment-checks`.
