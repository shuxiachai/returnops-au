# Founder decision HTTP boundary preparation

Owner: A Jingbo Chai. Designated human reviewer: C Yuwei Tao. This component prepares the frozen decision POST for later integration. It does not complete A2.07, A2.06, Gate 1 or personal/joint acceptance. The unchanged [work packages](08-delivery-work-packages.md) retain A2.07's start dependency A2.06.

## Explicit composition

The default `main.create_app` does not register this route. A trusted future composition may explicitly bind `compose_private_founder_decision_http(engine, auth_config)` to `register_founder_decision_candidate(app, request_ports_factory)`. Construction loads no settings or private environment, opens no database connection, and starts no workers. Duplicate POST path or effective operation ID (explicit or generated by FastAPI) registration fails before adding a route.

The only candidate route is `POST /v1/founder/cases/{case_id}/decisions`, operation `recordFounderDecision`. A request-level preflight uses real F.03 current identity and case access through a read-only `CustomerUnitOfWork`. It requires the current registry role FOUNDER and the same actor for session and decision authorization. It closes before parsing the body. It does not obtain a Domain business capability, commit, write a cursor or denial audit, or carry a cached grant into the decision service. The selected existing private service independently reauthorizes and applies its own transactional guards.

## Request and response boundary

Authorization and current case access precede body reads. Duplicate Authorization, Idempotency-Key or Content-Type headers and all query parameters are rejected. The original key is forwarded unchanged; the server creates the correlation ID. Existing bounded JSON decoding rejects duplicate members, invalid UTF-8 and non-finite/fractional numeric values. The frozen `FounderDecisionRequest` rejects unknown fields and permits exactly one target: proposal ID/version, processing failure, or order-lookup block. Only manual handling permits either non-proposal target. APPROVE requires the caller's actual retained preview ID and exact fingerprint; other decisions forbid those fields. Client actor, role, grant, command, provider and approval fields confer no authority.

Fixed dispatch selects one existing approve, reject, revision or manual service and invokes `accept` exactly once. It never invokes recovery, retries, wakes a worker or dispatches a provider. ACCEPTED returns 202 only for a frozen `DecisionReceipt` matching the requested case and decision, including the schema's approval-ID rule. It does not assume receipt version equals request version plus one; a retained replay may describe historical acceptance. 202 means acceptance, not completion.

Supported denials retain the static mapping: UNAUTHENTICATED 401; FORBIDDEN 403; NOT_FOUND 404; STALE_CASE_VERSION, IDEMPOTENCY_CONFLICT and INVALID_STATE 409; VALIDATION_ERROR 422; INTERNAL_ERROR 503. Supplied exception messages/status values are discarded. ReceiptUnavailable is normalized to INVALID_STATE without claiming that the adapter has located a retained receipt. UNKNOWN, unknown codes/statuses, malformed wrappers/receipts and unexpected exceptions produce safe 503. UNKNOWN never reads a receipt or triggers recovery. Errors contain empty details, server correlation and `Cache-Control: no-store`; 503 preserves the instruction to keep the original key. The adapter itself does not automatically retry.

## Offline evidence and limits

The new test module uses an isolated ASGI application with no lifespan and real F.03 Authenticator/AuthorizationService, short signed synthetic JWTs and synthetic registry/resource readers. Scripted ports provide result variants. Preflight uses an explicit synthetic read-only UoW so no PostgreSQL operation occurs. Actual database connections, real Domain accept/recover calls and external socket connections are guarded. Every guarded call is counted and teardown requires zero, including recovery and preflight commit attempts; an exception converted into 503 cannot hide one. Private configuration loaders and private `.env` file opens are similarly blocked and counted. Event-loop construction may create its own local socketpair before request guards; this is not provider or database access. No application startup is allowed. Repeated-key tests prove only unchanged forwarding, not persistent idempotency.

The execution receipt outside the candidate records exact commands, source hashes, collected nodes and actual outcomes. No previous CI result is relabelled as this component's result. All pre-existing source, contracts, migrations, requirements, CI and default registration stay unchanged.

Local database and Docker work remain paused. Default registration requires that later bounded integration and acceptance work.
