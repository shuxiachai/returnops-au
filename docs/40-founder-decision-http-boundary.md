# Founder decision HTTP boundary preparation

Owner: A Jingbo Chai. Designated human reviewer: C Yuwei Tao. This component implements A2.07's public Founder decision boundary: the frozen decision POST, its explicit composition and a real-database test module whose first actual outcomes are the CI receipt of this pull request. It does not complete A2.07, Gate 1 or personal/joint acceptance, which remain the designated human review. The unchanged [work packages](08-delivery-work-packages.md) retain A2.07's start dependency A2.06.

## Explicit composition

The default `main.create_app` does not register this route. Registration is an explicit choice: the keyword `enable_founder_decisions=True`, or the environment flag `RETURNOPS_FOUNDER_DECISIONS=1` (default `0`; any other value is rejected at startup), binds `compose_private_founder_decision_http(engine, auth_config)` to `register_founder_decision_candidate(app, request_ports_factory)`. The factory reads the trusted engine and auth configuration from application state at request time, exactly like the Founder reads, so construction loads no settings or private environment, opens no database connection, and starts no workers. The private demo server exposes the same choice as `demo.py serve --founder-decisions` (default off, like `--fixed-proposal`); the health-only `compose.yaml` environment has no auth file, so its business routes answer 503, and it stays unchanged. Duplicate POST path or effective operation ID (explicit or generated by FastAPI) registration fails before adding a route.

The only candidate route is `POST /v1/founder/cases/{case_id}/decisions`, operation `recordFounderDecision`. A request-level preflight uses real F.03 current identity and case access through a read-only `CustomerUnitOfWork`. It requires the current registry role FOUNDER and the same actor for session and decision authorization. It closes before parsing the body. It does not obtain a Domain business capability, commit, write a cursor or denial audit, or carry a cached grant into the decision service. The selected existing private service independently reauthorizes and applies its own transactional guards.

## Request and response boundary

Authorization and current case access precede body reads. Duplicate Authorization, Idempotency-Key or Content-Type headers and all query parameters are rejected. The original key is forwarded unchanged; the server creates the correlation ID. Existing bounded JSON decoding rejects duplicate members, invalid UTF-8 and non-finite/fractional numeric values. The frozen `FounderDecisionRequest` rejects unknown fields and permits exactly one target: proposal ID/version, processing failure, or order-lookup block. Only manual handling permits either non-proposal target. APPROVE requires the caller's actual retained preview ID and exact fingerprint; other decisions forbid those fields. Client actor, role, grant, command, provider and approval fields confer no authority.

Fixed dispatch selects one existing approve, reject, revision or manual service and invokes `accept` exactly once. It never invokes recovery, retries, wakes a worker or dispatches a provider. ACCEPTED returns 202 only for a frozen `DecisionReceipt` matching the requested case and decision, including the schema's approval-ID rule. It does not assume receipt version equals request version plus one; a retained replay may describe historical acceptance. 202 means acceptance, not completion.

Supported denials retain the static mapping: UNAUTHENTICATED 401; FORBIDDEN 403; NOT_FOUND 404; STALE_CASE_VERSION, IDEMPOTENCY_CONFLICT and INVALID_STATE 409; VALIDATION_ERROR 422; INTERNAL_ERROR 503. Supplied exception messages/status values are discarded. ReceiptUnavailable is normalized to INVALID_STATE without claiming that the adapter has located a retained receipt. UNKNOWN, unknown codes/statuses, malformed wrappers/receipts and unexpected exceptions produce safe 503. UNKNOWN never reads a receipt or triggers recovery. Errors contain empty details, server correlation and `Cache-Control: no-store`; 503 preserves the instruction to keep the original key. The adapter itself does not automatically retry.

## Evidence and limits

The offline module `tests/founder/test_decision_http_boundary.py` uses an isolated ASGI application with no lifespan and real F.03 Authenticator/AuthorizationService, short signed synthetic JWTs and synthetic registry/resource readers. Scripted ports provide result variants. Preflight uses an explicit synthetic read-only UoW so no PostgreSQL operation occurs. Actual database connections, real Domain accept/recover calls and external socket connections are guarded. Every guarded call is counted and teardown requires zero, including recovery and preflight commit attempts; an exception converted into 503 cannot hide one. Private configuration loaders and private `.env` file opens are similarly blocked and counted. Event-loop construction may create its own local socketpair before request guards; this is not provider or database access. No application startup is allowed. Repeated-key tests prove only unchanged forwarding, not persistent idempotency.

The real-database module `tests/founder/test_decision_http_postgresql.py` runs only where `DATABASE_URL` points at the PostgreSQL 17 service (CI's job service). It composes the application with `enable_founder_decisions=True` on the shared test engine and the registry identities of the lifecycle component, prepares cases with that component's own helpers, and drives HTTP, Domain service and database together. It asserts: each of the four decisions and both manual targets is accepted once with a 202 frozen receipt and its effect in the database, a same-key same-body replay returns the identical receipt, and a same-key different-body request is denied 409 IDEMPOTENCY_CONFLICT (DH01); a stale expected case version is denied 409 STALE_CASE_VERSION and a wrong scope fingerprint or an unretained preview ID 409 INVALID_STATE, each leaving the business snapshot unchanged, with three FOUNDER_APPROVE_DENIED audits after the three denials, after which the exact retained scope is still approved (DH02); client-supplied approval or actor fields, a missing Idempotency-Key, query parameters and preview fields on a non-APPROVE decision are rejected 422, a customer token 403 and no token 401, none writing a decision, approval or denial audit (DH03); two threads posting the same key and body concurrently produce exactly one decision and one approval, with responses limited to 202 (identical bodies) or 503 INTERNAL_ERROR carrying the keep-the-original-key message, never 409 (DH04); the accepted decision is visible through the Founder reads (DH05); the default composition answers 404 on the same database (DH06); and a Founder session revoked after the preflight is denied 401 UNAUTHENTICATED by the service's own fresh authorization with no effect (DH07). The CI receipt of each run records the actual outcomes; this document relabels none of them.

The execution receipt outside the candidate records exact commands, source hashes, collected nodes and actual outcomes. No previous CI result is relabelled as this component's result. Apart from the explicit flag in `main.create_app` and `demo.py serve`, pre-existing source, contracts, migrations, requirements, CI and default registration stay unchanged.

DEFERRED: preview or approval expiry and UNKNOWN commit, recovery and retention at the HTTP layer (the composition accepts no clock or unit-of-work injection; the existing Domain approve and reject series cover them); cases of another store (the shared fixtures provision one store); authorization or version loss during the body read itself; installed-process and complete regressions/cloud verification; actual model/C/provider integration; the full execution trace through A2.06 notification. Local database and Docker work remain paused. Default registration requires that later bounded integration and acceptance work.
