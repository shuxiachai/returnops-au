# ReturnOps AU：可执行工作包与验收清单

> 状态：Planned；本文件列出计划与验收条件，不代表功能已经实现。功能归属与边界的唯一来源是 [固定分工方案](07-frozen-work-allocation.md)，需求依据为 [v1.0 候选基线](00-project-definition-v1.md)。候选基线的正式采纳条件不因本清单创建而改变。

## 1. 使用约定

- `A/B/C` 分别表示成员 A、B、C；每行只有一位 Owner 和一位非作者 Reviewer。Review 不能代替 Owner 的个人实现与课程贡献。A 的默认 Reviewer 为 C，B/C 的默认 Reviewer 为 A。
- `A1.01` 等是本地稳定工作包 ID，不是 Jira key。所有条目的 Jira key 当前均为“未映射”；由 C 先核对现有 Jira/GitHub 记录，再建立或复用双向链接。不要猜测 `KAN-*`，也不要把同一交付物重复建卡。
- 这是一份 89 项检查清单，不要求建立 89 张独立 Jira 卡。可把同一功能、同一 Owner 的相关条目放在一张 Story/Issue 下；仍须保持子项 ID、验收与证据可定位。
- 计划时以约 2–4 小时的可评审工作段为拆分尺度，不是承诺每行都在该时间内完成。领取时发现工作段过大，继续拆成如 `A2.04.a`、`A2.04.b`；保留其所属功能、责任人和原验收目标。先做估时再排期，本文件不硬设日历截止日期。
- `S` 为开始依赖：前置项通过验收后，才开始本项的集成实现。`F` 为完成依赖：可先按约定契约编写草稿、mock、离线实验或测试，但必须等待这些前置项通过验收并完成对接后才能验收本项。两列都属于有向依赖，均不得循环；`—` 表示无额外条目依赖。所有已列 S 依赖也必须在本项完成前满足。
- 各组默认继承该组的 Requirement、Use Case 和 UML 映射；实际 Issue/PR 中要补上具体文件、图名、测试与运行链接，不得只写一个大范围 FR 列表。
- 现有代码、文档、PR 和评审是可复用成果。Owner 先将既有成果映射到条目，Reviewer 核验后记录其真实进度；不重置他人贡献，也不因已有文件或四个旧 schema 测试就认定新的安全功能完成。
- 本文件不维护实时状态、阻塞、负责人请假情况或截止日期。Jira 记录这些动态信息；GitHub 记录实现、评审与验证证据。每人更新自己的进度，C 维护工具配置与链接质量。
- 本文所有运行数据均为合成或去标识化数据，所有业务操作均为模拟或明确授权的 provider sandbox/test 操作。真实付款、生产订单修改及收费物流不在范围内。
