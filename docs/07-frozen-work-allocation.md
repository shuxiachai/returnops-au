## 1. 固定什么，不固定什么

从本次决定起，功能归属以本文件为准，检查项以 `docs/08` 为准。
旧文件中的七 AI 角色、B/C 仅做零碎支援、C 包办所有测试、三个已选
optional 全部留到课程之后等表述，不再用于分配新工作。

固定以下内容：

- 单一澳大利亚实体商品网店、一位 Human Founder、三种 AI 业务角色。
- 一案对应一个订单及一个或多个商品项；一个退货包裹对应一个模拟标签。
- 三人各自实现两项核心功能和一项选定 optional，共九项功能。
- A/B/C 预计投入约 45%/27%/28%。这是计划，不是评分比例、工时保证或按代码行数计算的贡献。
- AI 只提供结构化结果；Domain Service 是业务状态的唯一写入入口；Founder 是高影响操作的唯一批准者。
- 自动化终点为获批的模拟退货/标签及结果通知；不发生真钱、真实收费物流、生产订单或库存变更。
- 30 个双人复核 Gold 案例、正式 `B1 vs B4`、参数化安全/工作流测试；不要求 100 场景或 B2/B3。
- 冻结研究证据附录；报告只做约一至两页摘要，运行期小语料不等于继续扩写研究。

文件拆分、页面布局、内部命名和不影响契约的提示词改进由负责人处理。
新增/删除功能、改变负责人、改变公共接口语义、弱化安全或验收条件、扩大技术栈
或把课程交付后置，必须按第 9 节确认。发现 bug 属于修复，不重新讨论整个项目方向。

### 2.1 A1 — 案件生命周期、信息整理和提案生成

- **输入：**客户原文及期望结果、可选订单号/证据、补充回答、只读订单结果、C 的检索/审查结果。
- **A 实现：**领域模型、数据库迁移、合法状态转换、案件 API、只读订单适配器、Coordinator、Assessment、全局编排、案件审计。
- **信息规则：**原始陈述不可被 AI 覆盖；问题类别、客户期望、可能依据、评估状态和系统建议分别存储。
  证据逐项区分存在、缺失、冲突、不适用；支持合理购买凭证替代，按场景提问。
- **输出：**可重建案件、明确补充问题、引用原始陈述的版本化非执行性提案。
- **交接：**Assessment 调 C1 获得材料；编排器在提案生成后调用 C2；修改产生新版本并重新审查。
- **验收底线：**订单五类合同结果有测试；缺失/冲突不编造；多商品不变成拆分发货；AI 不能写权威状态或调用 Operations。
- **不包含：**C 的检索/风险实现、B 的页面、真实电商订单接入、最终法律权利认定。

### 2.2 A2 — 精确审批与受控模拟执行

- **输入：**可信 Founder 身份、当前案件/提案/风险结果、四种人工决定、准确操作范围。
- **A 实现：**服务端认证与授权、Approval Guard、决定记录、模拟退货/标签/通知提供方、幂等与核实恢复。
- **批准绑定：**案件、提案 ID/版本、命令集合、参数指纹、适用金额上限、有效期和可信操作者。
  同时核验提供方权限；不能只信前端的角色、批准标志或禁用按钮。
- **风险规则：**`ESCALATE` 不可直接批准执行；必须经过新提案和新的 `PASS`/`PASS_WITH_WARNING`。
  审查失败、超时、不合格式、过期均不得默认放行。
- **输出：**决定与执行记录、提供方编号/指纹/结果、通知、审计轨迹。拒绝和人工处理也须记录并通知。
- **验收底线：**无效授权在副作用前拦截；重复 key 至多一次效果；未知超时先 `UNKNOWN/RECONCILING` 核实；
  通知重试不重复退货；成功执行路径只有在结果保存且通知成功后才算完成。
- **不包含：**真实退款、库存/生产订单修改、真实收费物流、物理收货或财务结算。

### 2.3 A3 — 独立物流 sandbox/test-mode 适配器

- **新增贡献：**在稳定的核心 provider 接口后接入一个独立物流提供方测试环境，转换请求、编号、结果及错误，支持结果核实和受控恢复演示。
- **前置条件：**合法且可用的测试端点、测试权限、明确无真实发货/收费。先验证可获得性；不在文档里假定已有凭据。
- **验收底线：**同一套审批/幂等规则下切换适配器；有提供方测试调用与恢复证据，秘密信息不入库。
- **不能重复认领：**核心 Mock、核心幂等、核心超时测试不是本项的独立增量。
- **依赖失败：**保持未完成并在 Jira 记录阻塞，不改用生产权限。替换功能须组长批准并确认课程适配，不静默用另一个 Mock 充数。

### 2.4 B1 — 客户申请与补充信息门户

- **输入：**A 提供的申请/附件/补充接口与错误契约；Coordinator 返回的问题。
- **B 实现：**原文、可选订单号和期望结果的表单；附件上传/预览；补充问答；加载、错误、重试和回执。
- **输出：**符合契约的申请和补充回答；补充进入原案件，显示服务器确认的结果。
- **验收底线：**完整/不完整申请可走通；失败不会显示成功；重复点击有保护，服务器仍独立负责幂等；附件问题可恢复。
- **不包含：**完整客户账号中心、长期追踪门户、通用聊天机器人、前端业务状态机替代后端规则。

### 2.5 B2 — Founder 审核工作台

- **输入：**A 的权威案件、提案、引用、风险、审批、操作、通知和审计 API。
- **B 实现：**列表与详情；客户期望和系统建议分别展示；引用定位；当前版本、风险、不确定性；
  `APPROVE/REJECT/REQUEST_REVISION/MANUAL_HANDLING` 四种交互及批准范围确认；结果和历史展示。
- **输出：**绑定页面所示版本的决定请求，以及服务器确认后的结果界面。
- **验收底线：**旧版本、无权限、风险升级、通知失败均正确展示；刷新不能丢失服务器状态；点击批准不等于执行完成。
- **不包含：**前端产生可信 ApprovalRecord、自行判断法律权利、绕过服务端审批或从浏览器直连数据库/操作提供方。

### 2.6 B3 — 运营统计页面

- **固定内容：**案件总数、当前案件状态分布、每案最新风险审查结果分布、已记录的提案生成耗时。
- **数据边界：**A 提供查询/聚合接口，B 展示；无审查结果单列，不当成通过；不把历史多次审查当成多个案件。
- **耗时口径：**完整输入被接受至可供 Founder 审阅的提案存储；保留机器处理/风险循环，排除人工和物理等待。
  缺数据、失败和样本数明确展示，不能只挑成功案例作全系统性能结论。
- **验收底线：**用固定样例可对账；空数据/错误有提示；页面只读且受 Founder 权限保护。
- **不包含：**财务报表、复杂预测、独立统计数据库或 Grafana 平台。

### 2.7 C1 — 版本化检索与引用核验

- **输入：**A 的结构化案件查询；小型、已审阅的政策与消费者指导语料。
- **C 实现：**语料整理与加载、关键词/BM25 检索、引用位置/内容/版本核验、无结果与冲突信号。
- **输出：**来源 ID/类型、适用时的版本、访问日期、定位、内容 hash、检索时间、原文片段和核验结果。
- **边界：**C1 验证来源及引用的可解析性和一致性；C2 检查引用是否实际支持提案主张；A 验证提案结构与版本。
- **验收底线：**来源元数据齐全；错误/失效引用可识别；冲突保留并交审查；没有证据时不编造。
- **不包含：**继续扩写研究附录、全网爬取、向量检索扩展、案件/提案状态写入。

### 2.8 C2 — 独立风险审查

- **输入：**明确绑定提案 ID/版本的提案、证据、所引原文、语料版本；不读取生成器的隐藏推理。
- **C 实现：**独立系统提示词与模型调用；支持性、冲突、缺失、范围、低置信度、注入和越权检查。
- **唯一结果集合：**`PASS`、`PASS_WITH_WARNING`、`REVISE`、`NEEDS_INFORMATION`、`ESCALATE`。
- **输出：**结构化结论、问题依据、需要修改/补充的内容和版本信息；调用错误与业务结论分开。
- **验收底线：**覆盖五种分支和失败输出；没有正确版本和证据不能放行；不能修改提案或直接批准/执行。
- **交接：**A 判断结果对当前案件是否仍有效并进行流程路由；C 不维护第二个业务状态库。

### 2.9 C3 — 图片证据辅助提取

- **输入：**由 A 授权、校验并受控提供的合成/去标识化附件。
- **C 实现：**图片可见信息提取、原图引用、不确定性、无法判断处理；独立测试模糊/无关图片。
- **输出：**可供 Assessment 使用的结构化观察；不把图像观察当成已确定事实或最终责任判断。
- **验收底线：**保留原图关联；附件文字也是不可信输入；无法判断明确输出，不自动决定退款/拒绝。
- **阶段：**文本流程稳定后接入，但仍在课程提交前完成；不是第四个业务 AI 角色。
- **不包含：**重建上传服务、自训视觉模型、欺诈自动拒绝、真实个人图像处理。

## 5. 测试与评测责任

- A：状态、身份/附件权限、审批负例、幂等/并发、提供方失败与恢复、隐私清理、审计和接口集成。
- B：表单/附件/补充问答、四种决定、旧版本/无权限/失败展示、真实接口 E2E。
- C：检索/引用/风险/图片单元与合同测试；标签指南、运行器、B1/B4 结果汇总。
- 全组：跨模块故障复现、案例标注复核、失败分析和报告证据。C 统筹不是 C 包办。

开发使用 10–20 pilot，与正式 30 Gold 分离；Gold 标签不得用于调提示词。
20 个学生操作者计时案例是 30 Gold 的子集：A/B 先在未接触答案时分别计时，之后再参与标签复核。
双方计时输出均提交锁定之前，不查看对方输出，也不接收基于 Gold 的评分反馈。
C 在读取任何计时答案前（包括作为 E.03 Reviewer），必须密封保存全部 30 例初始标签、来源和理由，记录输入版本、标签版本/hash 与封存时间；标签内容不公开给 A/B。
E.02 只向 A/B 提供不含答案的封存凭证。两人的输出锁定后，仍按 E.05 正式交接 → A 逐例复核 → B 仲裁 → E.08 最终 hash 冻结和评分的原顺序推进。
复核或仲裁修改须保留初始版本、差异及来源/标签指南依据；不能按计时答案的匹配程度修改标签，最终冻结前不展示答案对比或评分。
每例一人标注、另一人复核、第三人仲裁；不要求第三人对无争议案例再做一轮签字。

`B1` 是无检索、无操作权的离线单 LLM 提案基线；`B4` 是完整受治理系统。
二者在同一正式案例和底层模型条件下运行，保持其规定的架构差异；不能为“公平”偷偷给 B1 加检索。
结果只解释为整套架构对比，不宣称隔离了多智能体拆分的因果收益。
报告原始计数、分母、失败例、环境和数据/语料/prompt/model/config/commit 版本；目标不是已测结果。

## 6. 三项交接验收

1. **共同数据契约：**案件、附件、提案、引用、风险、审批、操作、通知及错误有明确字段/版本。
   各模块提供正常和异常样例，能通过同一契约检查。实现路径可调整，公共语义不能静默改变。
2. **A ↔ C：**先检索、再生成提案、再独立审查；五种结果能路由；失败与过期结果不可当成通过；
   C 的结果不直接形成 ApprovalRecord/ToolCommand。
3. **A ↔ B：**页面所示版本与提交版本一致；重复提交、旧版本、无权限有可显示的响应；
   审批、操作和通知状态分开，页面只读服务器事实。

接口草案足以让 B 用 mock API、C 用合同样例并行开发。真实集成需通过相应契约和安全验证。
Gate 1 用固定提案/模拟审查输入验证确定性安全流程；LLM 接入执行链必须在 Gate 1 通过后。
C 的离线风险/检索开发、A 的离线角色输出试验及 B 的页面开发无需等 Gate 1 才开始。

## 8. Jira/GitHub 落地与完成定义

- 九个功能是分工边界，不要求九个新 Epic。A 主持核对和维护现有映射，C 按 R.04 核验证据；有合适记录就更新/关联，不重复创建。
- `docs/08` 的细任务是可验收检查项，不是必须批量建卡的命令。每次只选择当前可执行的少量工作包。
- 同一负责人、同一交付结果且同一 PR 可审阅的检查项可放在一张 Jira 交付卡内；跨负责人或可独立验收的成果再分卡。
- 每张交付卡有单一 owner、非作者 reviewer、依赖、实际估算、验收、WBS ID、真实 Jira key 和 GitHub 链接。
- 未查询的 Jira key 写“待映射，由 A/C 核验”；不得编造 KAN 编号、状态或过去工作记录。每项最多一个实际执行主卡。
- Jira 保存状态历史，GitHub 保存技术细节和证据；不维护另一个 GitHub Project 状态板，也不复制整份长文。
- 每人同时最多一项主实现工作；设计/评审/小型权限调查可并行，但不得虚报已开始或已完成。

每次交付使用同一最小评审包：WBS ID/实际 Jira key、具体 commit 或文件版本、相关 FR/NFR 与 UML、可复现证据及未决项。未提交候选可用明确版本和文件 hash 定位，不编造 commit 或 PR；证据区分静态检查、mock/stub 与真实运行。沿用原 Owner/Reviewer，普通反馈在同一交付项继续修复；触及第 9 节边界才进入相应变更确认，不为常规修改逐步重新请求分工。实际估时和 review 预约仍由当事人提供。

**Done 必须满足：**实现或文档交付存在；需求→模型→实现→测试→证据可追踪；正常及主要异常验收通过；
无秘密/真实个人数据；干净环境可复现；非作者完成审阅；代码 PR 合并或非代码成果获批；Jira 附真实证据。
仅写好计划、完成静态页面或让四个旧 schema 测试通过都不等于整项功能完成。

## 9. 冻结与变更规则

| 变化 | 处理方式 |
|---|---|
| 文案、布局、内部文件拆分、实现缺陷修复 | 负责人在正常 PR 中处理；不重开产品方向 |
| 公共接口语义/字段兼容性、任务依赖变化 | 相关生产/消费双方审阅；A 确认兼容或迁移方案；同步契约和测试 |
| 功能增删、负责人变更、验收降低、范围/安全/评测规模改变、optional 替换 | 记录一条变更说明：原因、受影响 ID、收益/成本/课程影响、批准者；A 明确批准，受影响成员确认，涉及课程适配时向 tutor 确认 |

修订 `07/08` 时保留稳定 ID；拆小任务使用后缀并记录原 ID 去向，不删除历史成果或重新计算作者。
实际工时偏离比例先减少不必要的实现复杂度、拆分支持工作并记录；不能未经同意把 B/C 的独立功能交给 A 代做。
计划冻结不是禁止修 bug，也不是在证据证明不可行时继续硬做。
